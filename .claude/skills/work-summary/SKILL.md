# work-summary

直前までやっていた作業を、後から見返せる形で「成果物としての記録」に残すスキル。Markdown と HTML の両方を出力する。

## いつ使うか

- 一連の作業（調査・実装・設定変更・デバッグなど）が一段落したとき
- ユーザーが「まとめて」「記録残して」「report 出して」「work-summary」などと言ったとき
- 明示的に `/work-summary` と呼ばれたとき

ユーザーが引数で topic（題材）を渡してきた場合はそれを使う。なければ会話から推測する。

## 出力先

**現在の作業ディレクトリ（cwd）配下** に以下を生成する：

```
<cwd>/work-summary/<topic-slug>-<YYYY-MM-DD>/
  ├── report.md
  └── report.html
```

- `<topic-slug>`: 作業内容を表す半角英小文字+ハイフンのスラッグ（例: `freee-journal-import`, `insights-report-fix`）
- `<YYYY-MM-DD>`: 当日日付（環境のcurrentDateを使う）
- 同じディレクトリが既に存在していたら、上書きせずユーザーに確認する

OneDrive 等の固定パスには出力しない（cwd 配下に作る）。ただしユーザーが明示的に保存先を指定した場合はそちらを優先。

## 記載する内容

両方のファイルに同じ内容を載せる。セクション構成は以下：

1. **作業の目的・背景** — なぜこの作業をしたか。前提・きっかけ・関連する課題。
2. **実施した内容** — 何をどうやったか。実行した主要なコマンド・手順を時系列で。
3. **変更したファイル一覧** — 追加/変更/削除したファイルを箇条書き。可能なら `git diff --stat` 相当の情報。
4. **結果・残課題・次のアクション** — 完了したこと、未完のこと、次にやるべきこと。
5. **作業内容のまとめ** — 全体の要約（数行）。

情報がない項目は無理に埋めず「該当なし」と書くか、ユーザーに確認する。憶測で書かない。

## 手順

1. `<topic>` を決める（ユーザー指定 > 会話から推測）。スラッグ化してディレクトリ名を組み立てる。
2. cwd を確認し、`work-summary/<topic-slug>-<YYYY-MM-DD>/` を作る。
3. 上記5セクションの内容を会話履歴・ファイル変更履歴から組み立てる。必要に応じて `git status` `git diff --stat` `git log` を確認。
4. `report.md` を書き出す。
5. `report.html` を書き出す。HTML はスタンドアロンで開けるよう `<style>` 埋め込みで読みやすく整形する（極力シンプル、emoji は使わない）。Markdown と同じ内容を HTML タグに置き換えたもの。
6. **`.gitignore` に `work-summary/` を追記する**（後述「.gitignore 追記」参照）。
7. 出力先の絶対パスをユーザーに報告する。

## .gitignore 追記（必須）

work-summary で生成したファイルは GitHub にアップロードしない方針。生成後、必ず以下を行う：

1. cwd が Git リポジトリ配下か確認（`git rev-parse --show-toplevel` などで）。リポジトリでなければスキップ。
2. リポジトリのルートにある `.gitignore` を確認。存在しなければ新規作成。
3. `work-summary/` のエントリが既にあれば何もしない。なければファイル末尾に以下を追記：
   ```
   # work-summary skill output (local-only, not pushed)
   work-summary/
   ```
4. 既に `work-summary/<topic-slug>-<YYYY-MM-DD>/` が `git add` 済みなら、ユーザーに警告（自動で `git rm --cached` はしない）。

ユーザーが「今回は git に入れたい」と明示した場合のみこのステップを省略する。

## report.html のテンプレート方針

「アーティファクト風」の視認性が良いダッシュボード的レイアウトにする。Markdown 版と同じ情報を載せつつ、HTML 版では構造を視覚化する。

### 基本構造

- `<!DOCTYPE html>` から始まるスタンドアロン HTML（外部CSS/JS禁止、画像も埋め込みかなしで）
- `<meta charset="utf-8">` `<meta name="viewport" content="width=device-width,initial-scale=1">` 必須
- `<title>` は `<topic> - <YYYY-MM-DD>`
- 本文フォントは system-ui 系、行間 1.6、最大幅 880px、中央寄せ
- 全体に余白を取り、白背景＋淡いグレー(#f6f7f9)のセクション背景でカード感を出す

### ヘッダー（必須）

ページ最上部に「ヘッダーカード」を置く：
- タイトル（topic を人間可読な日本語で）
- サブ情報を横並びの「メタチップ」で表示: 日付 / 作業ディレクトリ / 種別（調査/実装/設定/デバッグ等）
- ヘッダーの下にひとことサマリー（1〜2文）を `lead` クラスで配置

### サマリーダッシュボード（必須）

ヘッダー直下に「サマリーカード群」をグリッドで配置（3〜4枚）:
- 完了タスク数 / 残タスク数 / 変更ファイル数 / 所要時間 など、その作業に応じた指標
- 各カードは大きい数字 + 小さいラベル
- `display:grid; grid-template-columns: repeat(auto-fit, minmax(160px, 1fr)); gap: 12px;`

### セクション

各セクション(1〜5)は「カード」として表現:
- 背景 #fff、角丸 12px、薄いボーダー(#e5e7eb)、内側余白 20〜24px、セクション間に 20px のギャップ
- セクション見出しの左に細い縦バー（accent color #2563eb 等）を付けて識別性を上げる
- 番号付きセクションは見出しに 01 / 02 のような連番ラベルをチップで表示

### コンテンツ要素

- 「変更したファイル一覧」はテーブル化を推奨: 列は[種別(新規/更新/削除)][パス][備考]。種別はバッジ（緑=新規/青=更新/赤=削除）で色分け
- 「実施した内容」のステップは番号付きの大きめタイムライン風: 各ステップを左に番号丸チップ + 右にタイトル/詳細
- 「結果・残課題・次のアクション」は2〜3カラムの並び: 完了 / 残課題 / 次アクション をそれぞれカードで横並び
- コードブロックは `pre` に背景 #0f172a・文字色 #e2e8f0 のダークテーマも可（地の文と区別しやすい）。短い code は薄いグレー背景の従来通り
- 重要なキーワードは `<mark>` ではなくバッジ風 `<span class="tag">...</span>` で

### 配色

- accent: #2563eb（青）/ success: #16a34a / warning: #f59e0b / danger: #dc2626
- ベース: #fff（カード）/ #f6f7f9（背景）/ #111827（本文）/ #6b7280（サブテキスト）/ #e5e7eb（ボーダー）
- 多色使いは避け、accent + 状態色（4色）程度に絞る

### その他

- 見出しは h1/h2/h3 のみ
- emoji は使わない
- アニメーション・JavaScript は不要（純HTML+CSSのみ）
- 印刷時にも崩れないように `@media print` で背景色を残す指定を入れる
- レスポンシブ: 画面幅 600px 以下ではグリッドを1カラムに畳む

## 守ること

- ユーザーが明示的に頼まないかぎり、git commit や push は実行しない（記録だけ残す）
- 生成物は **GitHub にアップしない方針**。必ず `.gitignore` に `work-summary/` を追記する（上記「.gitignore 追記」セクション参照）
- 機密情報（APIキー、トークン、パスワード）はレポートに含めない
- レポート内では絶対パスより相対パスを優先（cwd を基準とする）
- 作業ディレクトリが Git リポジトリでなくても動くこと
- HTML/MD どちらか片方が失敗してももう片方は完了させる
