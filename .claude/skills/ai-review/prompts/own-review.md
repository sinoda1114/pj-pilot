# 変更差分のレビュー

対象: $ARGUMENTS（空なら、ステージ済み・未ステージ・未追跡を含む未コミットの変更）

あなたはこの変更のレビュアーです。問題を見つけて、変更者が判断・修正できる形で報告してください。コードは変更しないでください。

## 1. 集める

1. 対象の差分を取得する（`git diff --cached`、`git diff`、`git status` の未追跡ファイル、または指定の範囲）。
2. 変更されたファイルは**全文を読む**。差分の行だけで判断しない。
3. 変更コードが参照している設定値・定数・ヘルパー・呼び出し先・呼び出し元は、**実装や値を開いて確かめる**。名前や一般的な慣習から挙動を推測しない。開いて確かめた値は、そのまま判定の前提にする（「デプロイ時に違うかもしれない」は判定を保留する理由にしない）。
4. 依存パッケージのインストール、ネットワークへのアクセス、ビルドやテストのためのパッケージ取得はしない。読み取りと、手元にあるものの静的な確認だけで判断する。

## 2. 見る（優先順）

### 2.1 セキュリティ
- 外部から来る値（リクエストのパラメータ・ヘッダ・Cookie・本文、ファイルの内容、環境変数、外部 API の応答、DB から読んだ利用者の入力）が、どこへ流れるかを追う。
- 危険な出力先ごとに、その出力先に合った無害化がされているかを確かめる。例: HTML（エスケープ）、シェルや子プロセス（引数配列、**環境変数**、作業ディレクトリも含む）、ファイルパス（正規化と基準ディレクトリの確認）、SQL・LDAP・XPath などの問い合わせ（パラメータ化）、セッション・認可に使う値、ログ、リダイレクト先、外部へのリクエスト先。
- ある出力先向けの無害化（例: HTML エスケープ）を、別の出力先（例: セッションや SQL）への対策とみなさない。
- 部品の選び方: 弱い暗号・ハッシュ・乱数・鍵長・モード、Cookie の属性、秘密情報の直書き、認証・認可の抜け。
- 「テスト用」「意図的」「サンプル」「上流由来」に見えても、それを理由に指摘を省かない。意図が読み取れる場合は注記として添える。

### 2.2 正しさ
- 条件の境界（以上・未満、最初・最後、空、0 件、上限）、null・未定義、型の取り違え。
- 例外・エラーの扱い（握りつぶし、戻り値や終了コードの見落とし、不正な入力での例外、エラー出力の混入）、資源の閉じ忘れ。
- 非同期の待ち忘れ、状態更新の順序、競合、キャッシュや下書きなど古い値の使い回し。
- 外部 API・ライブラリ・CLI の仕様どおりに使っているか（戻り値、ステータス、単位、時刻とタイムゾーン）。

### 2.3 設計・保守性
- 責務の混在、重複、後から壊れやすい書き方。指摘は具体的な不具合につながるものを優先する。

## 3. 区分と段

### 3.1 区分（セキュリティか、正しさか）
- **セキュリティ**にするのは、攻撃者が本来できないことを得られる場合だけ: 他の利用者やサーバの情報を読む、データを書き換える・注入する・コマンドを実行させる、認証・認可をすり抜ける、他の利用者に及ぶ資源の枯渇を起こす。
- 攻撃者の値が危険な出力先に届く指摘は、動作のバグとして書く場合でも、必ずセキュリティにする。
- 弱い部品（暗号・ハッシュ・乱数・鍵長・モード・Cookie 属性）の使用は、悪用の経路を示せなくてもセキュリティにする。
- 攻撃者の入力でそのリクエスト自体が失敗するだけの問題（例外、500、誤った表示）、資源の扱い、エラー処理の不備は**正しさ**に置く。情報漏えいとしてセキュリティにするのは、コードが例外の詳細や内部情報を応答に書き出していて、攻撃者がその経路を起こせる場合だけ。
- 固定の内部情報（インストール先のパス、バージョンなど）の表示は、攻撃者がそれで新たな読み書き・操作を得る経路を示せない限り強化提案にする。攻撃者の値で応答の内容が変わり、秘密やファイルの有無が分かる場合はセキュリティにする。
- 攻撃者の値の行き先が、攻撃者自身がもともと自由にできる場所（自分の Cookie、自分への正しくエスケープされた応答など）だけで、その値を信頼して使う処理をコードで示せない場合は、脆弱ではなく強化提案にする。サーバ側で信頼される保存先（セッション、DB、ファイル、ログ、他の利用者への出力）に入る場合は対象外。

### 3.2 段
指摘ごとに、次のどれかに分類する。**確信度が低いことを理由に捨てない。**

| 段 | 条件 |
|---|---|
| 脆弱・不具合（確定） | 外部の値が危険な出力先に届く経路、または誤った動作が起きる条件を、コードで示せる。弱い部品の使用は、悪用の経路を示せなくてもここに入れる |
| 要確認 | 経路や条件をコードで示したうえで、その上にある**名前で参照されている特定の1点**（関数、設定のキー、差分外の呼び出し元）だけが手元で読めない。確かめるべき点を書く |
| 強化提案 | 値域・鍵長・属性・構成などの設計パラメータへの懸念で、具体的な悪用や故障の経路を示せないもの。実行環境の仮定（古い実行環境なら、エラーページの設定次第など）に依存するもの。設定値がない・読めないときの既定値、フォールバック、到達しない分岐の中身も、その経路に実際に入ることをコードで示せない限りここに入れる |
| 安全 | 問題がない、または危険な出力先に届かない理由をコードで示せる |

- 主要な実装の既定動作と、仕様が公開されている標準・主要ライブラリの API の挙動は、既知として判定する（前提にしたことを根拠に書く）。これらを「要確認」の理由にしない。
- 「実害がない」「今は起きない」と判断するときは、その根拠がコード上で成り立つか確かめる。成り立つと示せなければ、段を下げずに残す。
- **今の呼び出し元が安全な値しか渡していないことは、段を下げる理由にしない。** 変更されたコード（関数・コンポーネント・エンドポイント・CLI など）が、受け取った値を無害化せずに危険な出力先へ渡す、または誤った動作をする作りなら、その単位の欠陥として「脆弱・不具合」にする。今の呼び出し元が安全であることは、根拠に注記として書く。
- 同じく、今のデータ・今の設定・今の実行環境でたまたま起きないことも、段を下げる理由にしない。外部データの形式が変わったとき、境界の値（日付の変わり目、上限件数、空）が来たとき、別の実行環境で動いたときに誤った動作をする作りなら「脆弱・不具合」にする。

### 3.3 深刻度（High・Medium・Low）

深刻度は、止めるかどうかを決める。見た目の印象ではなく、次の基準で付ける。

| 深刻度 | 基準 |
|---|---|
| High | ふつうの使い方・ふつうのデータで起きる、または攻撃者が起こせる。起きると、データの消失・破損、誤った結果が利用者に届く、主要な機能が動かない、セキュリティ上の被害（情報漏えい・改ざん・実行・認可の回避）のどれかになる。弱い暗号・ハッシュ・乱数などの部品の使用もここに入れる |
| Medium | 起きる条件が限られる（特定の操作の組み合わせ、境界の値、外部データの変化、特定の実行環境）が、現実に起こりうる。または、起きたときの影響が一部の機能・一部の利用者にとどまる |
| Low | 端のケース、見た目・文言・ログ・可観測性の問題、壊れた入力や異常な状態でだけ起きるもの |

- 「今の呼び出し元やデータではたまたま起きない」欠陥は、段は下げずに「脆弱・不具合」のまま残し、深刻度で表す（ふつうの使い方で起こりうるなら High、条件が限られるなら Medium）。

### 3.4 欠陥として扱わないもの

- 変更の目的どおりの振る舞い（コミットの内容・コメント・周りのコードから意図が読み取れる仕様変更）。気になる場合は設計の指摘として書き、欠陥にはしない。
- 差分より前からある問題（変更が触れていない箇所、関数を移しただけで中身が同じもの）。「共通の指摘」または参考として書き、判定には入れない。変更によって悪化・露出した場合は欠陥として扱う。
- テスト・ドキュメント・型注釈の不足、命名や書き方の好み。設計の指摘として書く。

### 3.5 共通の指摘
- 差分外の共通部品（ヘルパー、設定、フィルタ、実行環境）に起因する問題や、変更ファイルすべてに同じ形で当てはまり各ファイルのデータの流れに関係しない指摘は、「共通の指摘」の節に1回だけ書き、ファイルごとの判定には入れない。
- そのファイル自身のコードで脆弱と示せるものは、共通でも各ファイルの判定に入れる。

## 4. 報告（この形を守る）

### 4.1 判定表（変更されたファイルすべて。1件でも欠けたら不完全）

| ファイル | セキュリティ判定 | その他の最重段 | 根拠（1行） |
|---|---|---|---|
| path/to/file | 脆弱 / 要確認 / 強化提案 / 安全 | 不具合 / 要確認 / 強化提案 / なし | 理由 |

- 「セキュリティ判定」は、そのファイルで攻撃者の値が危険な出力先に届く経路があるか、弱い部品を使っているかを表す。これに当たる指摘の最も重い段を書く。それ以外の指摘（正しさ・設計、上の2つに当たらないセキュリティ上の懸念）は、深刻度に関係なくこの列を上書きせず、指摘の欄に書く。根拠に「届かない」と書いた行を「脆弱」にしない。
- セキュリティ判定が「安全」のファイルも、危険な出力先に届かない理由、または弱い部品を使っていない理由を根拠に書く。

### 4.2 指摘（件数の上限なし。重い順）

各指摘について:
- 段 / 区分（セキュリティ・正しさ・設計）/ 深刻度（High・Medium・Low）
- 場所（ファイル:行）
- 問題（何が起きるか）
- 根拠（値の流れ、または起きる条件。確かめた設定やヘルパーの中身を含める）
- 修正案

### 4.3 共通の指摘（あれば。§3.5）

### 4.4 結論

3段で結論を出す。

| 結論 | 条件 | 意味 |
|---|---|---|
| `BLOCK` | 深刻度 High の「脆弱・不具合」が1件以上ある | 直すまで push しない |
| `MUST-ADDRESS` | BLOCK に当たらず、深刻度 Medium・Low の「脆弱・不具合」または「要確認」が1件以上ある | 直すか、直さない理由を記録すれば push できる |
| `PASS` | 上のどれもない（強化提案と設計の指摘だけ、または指摘なし） | そのまま push できる |

結論の行には、BLOCK・MUST-ADDRESS の理由になった指摘の番号を列挙する。

最後の行には、機械が読むための行を 1 行だけ書く（装飾なし）: `VERDICT: BLOCK`、`VERDICT: MUST-ADDRESS`、`VERDICT: PASS` のどれか。
